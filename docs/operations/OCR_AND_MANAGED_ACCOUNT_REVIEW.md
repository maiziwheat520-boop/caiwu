# OCR 与受管账户复核操作

## 目标

离线识别账单截图，并在导入候选前拦截不完整字段；凡已提供过流水的个人或
公司账户都进入受管账户台账，受管账户之间的转账必须取得双边流水。

## OCR 预处理

1. 原始图片只放入一次性输入目录，不修改原件。
2. 在无网络、无数据库凭据的 `ocr-preprocessor` 容器中运行
   `scripts/preprocess_bill_images.py`。
3. 输出为私有 `ledgerbridge.bill-ocr.v1` JSON；终端只显示图片数、账单数、
   可复核数和摘要哈希，不显示账户或金额。
4. 只有账单号、周期、金额均存在且必要字段置信度不低于 85% 的账单可进入
   待复核候选。缺字段、低置信度或不支持版式必须留在预处理待办中。
5. 每个候选只绑定产生它的那一张原图。年度汇总等背景截图只留作上下文，
   不生成单笔账单。
6. 构建导入包时传入 `--ocr-observations <私有JSON>`；一旦提供该参数，旧的
   固定 Excel 单元格路径不再生成照片候选。构建器同时输出私有
   `hotel-payout-cutover.json`，用于审计“旧周汇总→逐笔 OCR 账单”和“平台结算→
   收款银行入账”两类关联；该文件不包含审批指令。

## 受管账户登记

- 用户提供过至少一份正式流水的账户自动登记为受管账户。
- 台账保存账户键、账户别名/尾号、归属人或归属公司，以及来源流水证据引用。
- 没有流水证据的账户不能仅凭交易备注自动登记。
- 个人账户和各家公司账户都进入同一个受管账户集合，但仍保留独立归属主体。
- 支付宝花呗、余额宝、账户余额以及微信零钱、零钱通属于平台内部子账户，由所属
  平台完整流水覆盖；它们不是需要另交账单的外部受管账户。

## 转账双边佐证

- 同一归属主体的两个受管账户互转：标记为“内部转账”。
- 不同公司或不同归属主体的受管账户互转：标记为“关联方转账”，不得当作
  同一主体内部划转直接抵消。
- 两种情况都要求另一账户出现同币种、反方向、等额、日期窗口内的流水。
- 只有单边流水时，候选状态为“需要另一账户流水”，不能确认成收入、支出或
  已完成内部转账。
- 双边匹配只提出配对建议，最终仍由人工确认；原始两侧流水永久保留。
- 酒店平台结算或提现也按内部资金流处理；必须在收款银行流水中找到对应入账，
  未匹配时提示补充或关联收款账户流水，并保留人工审核。

## 转账对象分类

- 转账对象必须来自结构化账户/对象台账，不从摘要里的“银行”“账户”“转账”
  或“投资理财”等词推断。
- `self_managed` 表示同一归属主体的受管账户；`related_party` 表示公司或
  关联方；两者都必须补齐双边流水后才能形成内部/关联匹配。
- `known_business` 包括已登记供应商、员工、股东或客户；按资金性质人工审核，
  不自动当作内部账户。
- `unknown` 保留普通转账人工审核。
- 平台内充值、赎回和余额互转由平台完整流水闭合；只有明确连接真实银行卡或
  外部账户时才要求银行流水。

## 酒店平台提现关联

- 旧周汇总只有在金额唯一对应到字段完整的 OCR 账单时，才以追加式 `IGNORE`
  审计事件标记为已被更精确候选替代；没有 OCR 替代项的旧候选继续保留待审。
- 导入前必须先对 OCR 原图加密并生成与源清单摘要绑定的 prepared manifest；
  原图证据、逐笔候选、旧汇总替换和银行入账关联在同一数据库事务中登记。
  缺少原图、密文或摘要不一致时整批失败关闭，不留下半导入候选。
- OCR 账单与银行入账必须同时满足：金额完全一致、银行入账日在结算周期结束后
  0–7 天、平台名称/支付机构线索一致、候选和入账均为一对一唯一匹配。
- 任一金额存在多个候选、平台线索不符、日期超窗或银行入账被重复占用时，整批
  关联失败关闭，不按最接近金额或最接近日期猜测。
- 成功关联只消除 `HOTEL_PAYOUT_STATEMENT_REQUIRED` 这一项材料风险；OCR 候选仍是
  待审核状态，不自动审批、不自动入账，银行候选也继续保留为独立原始证据。
- 当前五月真实测试数据中，携程与美团各 4 笔（共 8 笔）满足上述规则；两笔
  2026-05-25 至 2026-05-31 结算尚缺随后银行入账，需提供六月收款账户流水。

## 例外审核与批量确认

- 置信度只表示字段提取可靠程度，不表示交易本身没有业务风险。
- 只有状态为待审核、提取置信度不低于 90%、字段完整、没有阻断项且 Core
  没有给出风险标记的候选，才能进入网页“一键审批”。
- 转账、关联账户划转、酒店平台结算、未匹配退款/冲正和未最终结算状态不参加
  批量确认；网页必须显示原因并保留单笔人工审核入口。唯一匹配且已持久化审计
  关联的部分退款按净交易复核，不再让原支付和退款各占一条重复风险。
- 一键审批仍需用户明确确认。每一条候选分别使用版本检查、幂等键和追加式
  审计事件；批量确认不会直接生成正式凭证或自动入账。
- Core 未返回风险评估时，网页必须按风险评估不可用处理，禁止批量放行。

## 失败处理

- OCR 依赖不可用、图片超限、符号链接、非图片文件：拒绝处理。
- 日期被截图裁切：标记周期缺失，不推算最后一位。
- 对方是受管账户但找不到另一侧流水：提示补充对应账户明细。
- 对方不是受管账户：按外部交易继续分类，不伪造内部配对。
