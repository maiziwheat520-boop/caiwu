# ADR 0005: Database-owned payroll and reconciliation workbenches

- Status: accepted
- Date: 2026-09-28

## Context

Payroll authoring previously lived in a Windows/Tkinter workbook program and later in a
transitional HTTP provider with a file-backed TEST_ONLY workspace. Hotel reconciliation also
depended on a mutable Excel workbook. Both designs tie correctness or availability to a specific
computer, local path, spreadsheet cache, or separately persisted business state.

The user requires VM103 to be the stable runtime, the website to retain and display business
facts, and Excel to remain only as the final bank-remittance output.

## Decision

Payroll and reconciliation become independently maintained Modules in the LedgerBridge modular
monolith and share its PostgreSQL fact layer.

Payroll owns calculation drafts, blocking issues, employee/rule versions, immutable locked payroll
versions, and deterministic bank-file export. Reconciliation owns monthly/store/category views and
consumes only a versioned locked-payroll projection. Existing provider and workbook readers become
migration Adapters, not continuing sources of truth.

The website calls the Modules through versioned Interfaces. It does not reproduce spreadsheet
formulas or construct authoritative totals in the browser.

## Consequences

- Windows Excel recalculation is removed from payroll correctness.
- The bank remittance workbook is the only spreadsheet generated by Payroll.
- Reconciliation workbook import requires a controlled, idempotent migration with duplicate-fact
  detection and detail-to-total checks.
- Provider and workbook compatibility remain internal seams that can be deleted after parity and
  migration acceptance.
- Payment submission, automatic bank execution, and automatic accounting posting remain absent.
